## 1. 决策摘要

UX-A 至 UX-D 的工程验收结论为：**通过，可以进入后续批次；不存在需要回退或阻止主流程继续开发的 P0/P1 功能问题。**

本结论基于代码、自动化测试、真实 API、桌面/窄屏浏览器、隔离性能基准和数据安全边界的交叉验证，不等同于已经完成外部目标用户研究。

进入下一批前保留三个明确条件：

1. UX-D 当前仍是 `codex/ux-d` 分支上的未提交变更，应先形成可回退的 Git 历史边界。
2. 真实旧库有 1 条历史孤立 `annotation_classes` 元数据，只允许预览后显式修复，不在启动时静默删除。
3. “新用户 3 分钟内完成首次有效标注”仍需真实新手可用性测试；当前只能确认工程路径和界面语义具备支持条件。

## 3. 各角色意见、异议与决策

这里的“沟通”是基于项目目标和代码边界进行的角色化评审，不代表已经联系外部真实人员。

| 角色 | 主要诉求或异议 | 产品决策 |
| --- | --- | --- |
| 研究用户 | 长扫描和导出不能冻结页面，也不能修改原始文件 | 同意。下一主批次为本地任务中心；所有产物只写应用存储或临时目录 |
| 产品 | 是否应先做更多标注工具或近重复分析 | 不同意。核心流程已成形，先解决长任务、可取消、失败恢复和结果可信度 |
| UX | 任务中心可能变成复杂企业队列页面 | 同意控制范围。只增加全局状态入口和轻量抽屉，不新增常驻大仪表盘 |
| 前端 | 是否一次迁移扫描、导出、导入、缩略图和备份 | 不同意。逐类迁移；每类任务独立验收，避免状态模型和界面同时失控 |
| 后端 | `jobs` 是新持久化模型，继续启动时补列风险增大 | 同意。F2-0 先引入正式迁移与真实旧库升级验证，再增加 jobs |
| 数据安全 | 是否可自动清理旧孤立元数据、取消时删除原始文件 | 不同意。孤立元数据只做预览和显式确认；取消只清理应用临时产物 |
| 性能 | 是否通过多写者和大线程池加速 | 不同意。SQLite 继续单写者；hash/缩略图只使用受限并发，避免磁盘争用 |
| 测试 | 进程退出后的 running job 如何处理 | 不自动假装成功或盲目续跑。启动时标记为 interrupted/failed，并提供显式重试 |
| 可复现性 | 没有 dataset revision 时能否承诺导出完全复现 | 不能。F2 先固化任务参数、类别映射和查询范围；完整历史复现留给 E1 |
| 维护 | 是否现在迁移 PostgreSQL、Redis 或 Celery | 不同意。保持 React + FastAPI + SQLModel/SQLAlchemy + SQLite 模块化单体 |
| 发布 | UX-D 是否已经具备稳定历史边界 | 功能已通过，但尚未提交；开始 F2 前必须先建立 Git checkpoint |

## 5. 分批计划

### G0：UX-D 发布边界

目标：把已经验收的 UX-D 变成可回退、可比较的稳定基线。

工作：

- 复核 UX-D 变更范围，只包含当前查询、SQLite、缓存、基准、测试和文档。
- 建立一个连贯提交；不混入 F2 schema 或任务中心代码。
- 提交后重新运行后端全量测试、前端构建和 `git diff --check`。
- 保留当前真实数据库与原始数据，不把数据库、WAL、临时基准或前端构建产物纳入 Git。

完成门槛：

- 工作树只剩用户明确保留的改动。
- UX-D 可由单个明确 Git 边界恢复。
- 服务启动、API 和浏览器主链仍通过。

### F2-0：正式迁移与数据完整性

目标：为 jobs、revision 和后续持久化模型建立可靠升级路径。

工作：

- 引入 Alembic，生成与当前 schema 对齐的基线迁移。
- 验证两条路径：全新数据库创建、真实旧库副本升级。
- 增加只读完整性报告：外键违规、孤立 annotation class/tag/link、缺失表或列。
- 提供显式修复预览；只有用户确认后才清理孤立元数据。
- 迁移前使用 SQLite backup API 创建元数据备份，并验证备份可打开；不复制原始文件。

完成门槛：

- 迁移失败不会破坏原库，错误信息包含恢复路径。
- 真实旧库副本升级前后数据集、样本、标签、标注、split 和训练准备记录数量一致。
- 所有修复都有预览、确认和结果报告。
- 新旧数据库均通过全量 API 测试。

预计：2–3 个开发日。

### F2-1：本地任务中心基础

目标：建立持久化 job 状态机、runner、API 和轻量 UI，不迁移具体业务任务。

最小状态：

- `queued`
- `running`
- `succeeded`
- `failed`
- `cancelled`
- 进程意外退出后的 `interrupted`

最小字段：

- 类型、状态、数据集、阶段、当前进度、总量、错误数。
- 创建/开始/完成/更新时间、尝试次数、取消请求时间。
- 创建时参数快照、结果摘要、错误摘要、重试来源。

运行边界：

- 一个写任务通道；最多一至两个受限只读/CPU 任务。
- 每个任务独立创建 Session，不共享请求 Session 或连接。
- 取消是协作式检查点，不强杀线程。
- 启动时把遗留 running 任务标记为 interrupted，用户确认后重试。

API：

- 创建任务。
- 列表与详情。
- 请求取消。
- 重试终态任务。
- 清理已结束任务历史。

UI：

- 顶栏或全局区域显示运行数量与失败提示。
- 抽屉展示类型、进度、阶段、耗时、错误和操作。
- 不新增单独企业级任务首页。

完成门槛：

- 状态转换、取消、重试、进程重启恢复有自动化测试。
- 任务创建反馈 p95 小于 300 ms；状态查询 p95 小于 150 ms。
- runner 崩溃不让任务永久显示 running。
- 不修改原始文件。

预计：4–6 个开发日。

### F2-2：扫描任务与增量扫描

目标：把最常见长写任务迁移到任务中心，并降低重复扫描成本。

阶段：

1. 枚举文件。
2. 读取 stat 与类型。
3. 对新增或变化文件计算 hash。
4. 分批写入 SQLite。
5. 检测缺失记录。
6. 生成结果报告。

策略：

- 已登记文件先比较 size + mtime，未变化时跳过 SHA-256。
- 首次扫描或显式深度校验才全量 hash。
- stat/hash 使用受限线程池；数据库仍单写者、分批提交。
- 权限错误、损坏文件和不支持类型单独计数，不让整个任务失败。
- 取消后保留已提交的安全元数据批次，并明确报告部分完成；再次扫描应幂等收敛。
- 先增加异步任务 API，保留旧同步端点一个过渡周期，避免突然破坏调用方。

完成门槛：

- 隔离 20k/100k 文件基准记录枚举、hash、写入和总耗时。
- 完全未变化的第二次扫描跳过绝大多数 hash，结果与首次扫描一致。
- 中断、重试、权限错误、文件新增/变化/缺失均有回归。
- 抽样原始文件 hash 前后不变。
- 页面在扫描期间可继续浏览旧数据，并清楚标记数据正在更新。

预计：4–6 个开发日。

### F2-3：训练导出任务与有界内存

目标：让大型 COCO/YOLO/VOC/LabelMe 导出不占用长 HTTP 请求和完整内存对象。

工作：

- 任务创建时固化任务类型、格式、筛选范围、split、类别映射和空样本策略。
- 在完整 revision 落地前，只承诺“本次任务参数固定”，不承诺任意历史时点完全重建。
- 大 JSON/ZIP 使用应用临时文件或流式写入，不使用完整 `BytesIO` 常驻。
- 预检仍复用现有质量和格式契约；error 阻止任务运行。
- 成功后记录文件大小、hash、生成时间和结果报告。
- 取消或失败只清理应用临时产物，不触碰原始目录。
- 小导出旧端点保留过渡兼容，前端主流程切换到任务方式。

完成门槛：

- 所有现有训练格式产物内容与同步实现一致。
- 100k 样本导出峰值内存不随最终 ZIP/JSON 大小线性增长。
- 范围或类别配置在任务运行期间不会被界面后续修改污染。
- 取消、磁盘空间不足、临时文件失败和下载过期均有明确结果。
- 原始文件和原始目录无新增 sidecar。

预计：5–7 个开发日。

### F2-4：次级长任务逐项迁移

顺序固定为：

1. 缩略图：按内容 hash 缓存，当前页和少量预取优先。
2. 元数据/标注导入：dry-run、错误行诊断、分批写入和显式回滚策略。
3. 轻量备份：SQLite 元数据、任务配置和校验信息，不复制原图。

要求：

- 三类任务不在一个提交或一次验收中同时迁移。
- 每完成一类，先验证取消、失败、重试、恢复和数据安全，再进入下一类。

预计：每类 3–5 个开发日。

### E1：revision、快照与可复现性

目标：让训练产物可以解释“基于哪一版数据和配置生成”。

工作：

- dataset revision 与所有元数据写路径的统一递增规则。
- 轻量快照：manifest、文件 hash、标注、标签、split、class map、查询范围和导出配置。
- 快照比较：新增/删除/变更文件、标注和 split 变化。
- 从快照重建训练标签，不复制原始图片。
- stats、quality、duplicates、precheck 缓存绑定 revision。

完成门槛：

- 同一 revision 和配置可生成相同类别映射与训练标签 hash。
- 快照差异可追溯到具体样本。
- 快照失效不会返回看似最新但依据过期的数据。

预计：7–10 个开发日。

### E2：研究效率

按价值和依赖顺序：

1. 保存视图和可复用标注队列。
2. 跨 split 精确重复强化，再评估近重复/唯一性。
3. 离线 prediction 导入与样本级 false positive/false negative/IoU 评估。
4. 删除元数据的回收站或最近操作撤销。

不接外部 AI API，不强制 GPU，不引入向量数据库。

## 8. 风险与停止条件

- 如果 F2-0 无法可靠升级真实旧库副本，停止 jobs schema 开发，先解决迁移。
- 如果任务取消不能保证元数据一致，停止迁移下一类任务。
- 如果单写者下仍稳定出现 locked 错误，先定位长事务或连接泄漏，不直接迁移 PostgreSQL。
- 如果导出任务范围会随运行期间的数据修改漂移，停止发布导出任务，先固化 selection snapshot。
- 如果任务中心 UI 抢占详情页主流程，回退为全局状态入口和抽屉。
- 如果 100k/1M 目标下关键查询持续超过门槛，先用查询计划和 revision 缓存定位，不靠无限前端缓存掩盖。
